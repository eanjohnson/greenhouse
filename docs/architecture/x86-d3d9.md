# Direct3D 9

What this covers: how a Direct3D 9 game renders in Greenhouse. The console ships Microsoft's
`d3d9on12.dll` (the D3D9-to-D3D12 mapping layer) but not `d3d9.dll`. Greenhouse supplies the
missing half: the `IDirect3D9` / `IDirect3DDevice9` API layer, written against the mapping
layer's driver interface. It serves 64-bit guests directly and 32-bit guests through the x86 COM
layer.

Where the code is: `src/loader/gh_d3d9rt.h` (the runtime, namespace `ghd9`),
`src/loader/gh_d3d9.h` (driver loading, adapter open, probe, PSO log),
`src/loader/d3d9on12ddi.h` (the mapping layer's private interface),
`src/loader/gh_d3dx9.h` (a small D3DX subset), and
`src/loader/x86/gh_x86_com_d3d9.h` (the 32-bit face).

Related pages: [graphics.md](graphics.md) (the D3D12 bridge and presentation),
[x86-guest.md](x86-guest.md) (the 32-bit track), [engine-notes.md](engine-notes.md),
[../reference/knobs.md](../reference/knobs.md),
[../reference/diagnostics.md](../reference/diagnostics.md),
[../reference/known-limits.md](../reference/known-limits.md).

## 1. The split: what we implement, what the console does

On desktop Windows, Direct3D 9 is two layers. `d3d9.dll` is the runtime: COM objects, reference
counting, state tracking, parameter validation, swap chains. Below it is a user-mode driver that
speaks the D3D9 device driver interface (DDI). `d3d9on12.dll` is such a driver: it implements the
DDI on top of D3D12, including the conversion of D3D9 shader bytecode.

| Layer | Who provides it here | Notes |
|---|---|---|
| `Direct3DCreate9`, `IDirect3D9`, `IDirect3DDevice9`, textures, buffers, shaders, queries | Greenhouse, `gh_d3d9rt.h` | Written from the public API contract |
| D3D9 DDI (`D3DDDI_DEVICEFUNCS`: draw, state, resources, blits, locks) | Console `d3d9on12.dll` | Reached through its private table |
| D3D9 bytecode -> DXBC -> driver shader | Console `d3d9on12.dll` | We supply only the signing callback |
| D3D12 device, command queue, swap chain | The loader's graphics bridge (`g_gfx`) | Shared with every other guest path; see [graphics.md](graphics.md) |
| Fixed-function pixel stage 0 | Greenhouse (generated pixel shader) | Section 6 |
| Fixed-function vertex pipeline | Nobody | Draws without a vertex shader and without pre-transformed vertices are skipped |

`d3d9on12ddi.h` is Microsoft's published, MIT-licensed header for the mapping layer's private
entry points (`GetPrivateDDITable`, `D3D9ON12_PRIVATE_DDI_TABLE_VERSIONED`, the open-adapter
arguments and callbacks). Building also needs two Windows Driver Kit headers (`d3dumddi.h`,
`d3dkmthk.h`), which are fetched into a git-ignored directory and are not in the repository.

## 2. Driver loading and adapter open (`gh_d3d9.h`)

| Function | What it does |
|---|---|
| `LoadDriver` | Loads `d3d9on12.dll`, pins the module, and obtains the private table: the versioned entry point if present, otherwise the version-1 one |
| `OpenAdapter` | Calls `pfnOpenAdapter2` with `D3D9ON12_CREATE_DEVICE_ARGS2` naming the loader's existing `ID3D12Device` and command queue, plus our callbacks. Falls back to the version-1 open (no signing callback) |
| `PresentCb` | The driver's present callback. Unused for real presentation (section 8) |
| `SignDxbc` | Signing callback. The mapping layer converts D3D9 bytecode to a DXBC container and expects a signer DLL that the console lacks; this computes the container hash with the same routine the shader backporter uses ([dxil-backporter.md](dxil-backporter.md)) |
| `GetCaps`, `LogCaps` | Wrappers over the adapter's `pfnGetCaps` |
| `Probe` / `GhD3d9Probe` | Self-test, run from the Launcher when a file named `gh_d9probe.txt` exists in LocalState (deleted on use). Opens the adapter, creates a device, fills a 64x64 render target, reads it back. Lines are prefixed `D9P` |

The device is created on the loader's own D3D12 device, not a second one. Everything the D3D9
runtime draws is therefore visible to the bridge's swap chain without a cross-device copy.

`gh_d3d9rt.h: OpenAdapterOnce` runs once per process: bridge up, driver loaded, adapter open,
device-removal watch started, then the capability queries (`D3DDDICAPS_GETD3D9CAPS`,
format count and data, query count and data). It logs
`D9 adapter ready formats= queries= display= vs= ps=`.

## 3. Object model (`gh_d3d9rt.h`)

| Class | D3D9 interface | Notes |
|---|---|---|
| `D3D9` | `IDirect3D9` | One per process, never freed |
| `Dev` | `IDirect3DDevice9` | Owns the DDI device handle and all shadow state |
| `Swap` | `IDirect3DSwapChain9` | The implicit swap chain only |
| `Core` | (none) | One DDI resource: handle, type, format, pool, usage, dimensions, level and face counts, system-memory backing, managed-lock staging |
| `Surf`, `Volume` | `IDirect3DSurface9`, `IDirect3DVolume9` | One subresource of a `Core`; references forward to the container |
| `Tex2D`, `TexCube`, `TexVol` | The three texture interfaces | |
| `VB`, `IB` | Vertex and index buffers | |
| `Decl` | `IDirect3DVertexDeclaration9` | Remembers whether it has pre-transformed positions (`preT`) and its FVF, if built from one |
| `VS`, `PS` (`Shader<I,kPS>`) | Shaders | Keep a copy of the bytecode and a hash |
| `Query` | `IDirect3DQuery9` | |
| `StateBlock` | `IDirect3DStateBlock9` | Exists; `Capture` and `Apply` do nothing (logged once) |

Conventions used throughout the file:

- **`Obj<I>`** is the COM base. It keeps two counts: `ext` (the application's references) and
  `intl` (references held because the object is bound to the device). An object bound as a
  texture or render target survives the application's final `Release`, as D3D9 requires.
- **One lock.** Every method takes the recursive lock `Cs()` through the guard `Lk`. The runtime
  behaves as if `D3DCREATE_MULTITHREADED` were always set.
- **`DDI(dev, pfnName, args...)`** calls a driver entry inside a structured-exception guard,
  checks for a null entry, and logs the first few failures per entry as `D9 DDI <name> hr=`.
  Use it for every driver call.
- **`Once(key)`** logs the first occurrence of something unimplemented or unusual. Grep the diag
  for `D9 ` to see everything a title touched that the runtime does not do.

## 4. Adapter, device, swap chain

### `IDirect3D9` (`D3D9`)

| Method | Behaviour |
|---|---|
| `GetAdapterCount` | 1 |
| `GetAdapterIdentifier` | Driver `d3d9on12.dll`; vendor and device ids from the knobs `gh_d9_vendor` / `gh_d9_device` (defaults are a desktop AMD card, so engines pick a sane hardware profile) |
| `EnumAdapterModes`, `GetAdapterDisplayMode` | A fixed list from 640x480 to 3840x2160, capped at the display size, 60 Hz, `X8R8G8B8` and `A8R8G8B8` only |
| `CheckDeviceType` | HAL only |
| `CheckDeviceFormat`, `CheckDepthStencilMatch` | Answered from the driver's format table |
| `CheckDeviceMultiSampleType` | `D3DMULTISAMPLE_NONE` only |
| `GetDeviceCaps` | The driver's `D3DCAPS9` |
| `Direct3DCreate9Ex` | Fails (`D3DERR_NOTAVAILABLE`); games fall back to `Direct3DCreate9` |

### `CreateDevice`

`D3D9::CreateDevice` accepts HAL only, calls the adapter's `pfnCreateDevice` with interface
version 9, and requires the entries `pfnCreateResource2` and `pfnFlush1`. The mapping layer fills
only the WDDM 1.2-and-later entries (`CreateResource2`, `Flush1`, `Present1`); the older ones are
null, so code written against the legacy entries will fault.

`Dev::MakeSwapchain` then creates the implicit swap chain as ordinary render-target resources:
size defaulted from the display, format defaulted to `X8R8G8B8`, at most three back buffers,
multisampling forced off, and the automatic depth-stencil surface if requested. It logs
`D9 swapchain ...`. `Dev::Defaults` pushes the documented D3D9 default value of every render,
sampler and texture-stage state to the driver, because the driver starts from its own defaults.

`Reset` drops all bindings, rebuilds the swap chain and re-applies defaults. It always succeeds;
there is no lost-device state. `TestCooperativeLevel` always returns `D3D_OK`.

On teardown the DDI device is destroyed but the `Dev` object stays allocated and marked dead, so
objects the game releases late do not touch freed memory.

## 5. State, resources, shaders, draws

### State tracking

Every `Set*` stores the value in a shadow array and forwards it to the driver. Every `Get*`
answers from the shadow.

| State | Shadow | Pushed with |
|---|---|---|
| Render states | `rs[256]` | `PushRs` -> `pfnSetRenderState` |
| Sampler states | `ss[21][14]` (0-15 pixel, 16 displacement, 17-20 vertex) | `PushSs`; the DDI has no sampler-state call, so `kSampToTss` maps each onto a DDI texture-stage state |
| Texture-stage states | `tss[8][33]` | `PushTss` |
| Textures | `tex[21]` | `pfnSetTexture` |
| Streams, indices, declaration | `streams[16]`, `ib`, `decl` | `pfnSetStreamSource`, `pfnSetIndices`, `pfnSetVertexShaderDecl` |
| Shader constants | `vsF[256]`, `psF[224]`, 16 int and 16 bool each | `pfnSetVertexShaderConst*`, `pfnSetPixelShaderConst*` |
| Viewport, scissor | `vp`, `sc` | `PushViewport` (also `pfnSetZRange`), `PushScissor` |
| Render targets, depth | `rt[4]`, `ds` | `PushRt`, `PushDs`; setting target 0 resets the viewport |
| Clip planes | stored | `pfnSetClipPlane` |

Stored and returned, but never sent to the driver, because they belong to the fixed-function
vertex pipeline or have no meaning here: transforms, material, lights, clip status, gamma ramp,
palettes, N-patch mode, software vertex processing, cursor.

### Resources and pools

`CoreCreate` builds the `D3DDDIARG_CREATERESOURCE2` for every resource type.

| Pool | How it is realized |
|---|---|
| `DEFAULT` | A driver resource |
| `MANAGED` | A driver resource in video memory. No system-memory mirror is kept |
| `SYSTEMMEM` | A driver resource over memory we allocate (`Core::mem`) |
| `SCRATCH` | Our memory only; never reaches the driver |

`Fmt`, `Pitch` and `Rows` hold the format table, including the block-compressed formats
(DXT1-5, ATI1, ATI2). Add a format there first if a title uses one the table lacks.

### Locks (`CoreLock` / `CoreUnlock`)

| Resource | Lock returns | On unlock |
|---|---|---|
| System-memory or scratch | A pointer into `Core::mem` | Nothing |
| Managed | A CPU staging buffer for that subresource | A temporary system-memory resource is created over the staging buffer and blitted into the driver copy |
| Everything else | The driver's `pfnLock` pointer | `pfnUnlock` |

`D3DLOCK_DISCARD` and `D3DLOCK_NOOVERWRITE` are passed to the driver only for dynamic resources.
A read-only lock of a managed resource returns zeros, not the texture's contents (logged once);
nothing that runs today reads managed textures back.

### Copies

`UpdateSurface`, `StretchRect`, `GetRenderTargetData` and `ColorFill` map to the driver's blit
and fill entries; `UpdateTexture` to its texture and volume blits. `Clear` clips to the viewport
and scissor as D3D9 specifies. `GenerateMipSubLevels` works for 2D and cube textures.

### Shaders and declarations

`CreateVertexShader` and `CreatePixelShader` measure the token stream (`ShaderDwords`) and hand
the bytecode to the driver unchanged. `CreateVertexDeclaration` passes the element array through
(`MakeDecl`). `SetFVF` builds an equivalent declaration (`FvfDecl`) and caches it per device.

### Draws

`Dev::DrawOk` decides whether a draw can be issued:

| Bound state | Result |
|---|---|
| Pixel shader, and a vertex shader or a pre-transformed declaration | Drawn. For pre-transformed vertices the driver supplies its own vertex stage |
| Vertex shader below 3.0, no pixel shader | Drawn with a generated pixel shader (section 6), unless `gh_d9_ffps` is 0 |
| Anything else (no vertex shader and untransformed vertices; shader model 3 vertex shader without a pixel shader) | Skipped, counted, logged |

The four draw calls map to `pfnDrawPrimitive`, `pfnDrawIndexedPrimitive`, and for the
user-pointer variants `pfnSetStreamSourceUm` followed by the `...2` entries; the user-pointer
draws unbind stream 0 (and the index buffer) afterwards, as D3D9 does.

### Queries

Types the driver reports are forwarded. The vertex-cache query is answered locally. Others
return `D3DERR_NOTAVAILABLE`.

## 6. Fixed-function pixel stage 0

Direct3D 9 allows a draw with a programmable vertex shader and no pixel shader. The pixel colour
is then computed by the fixed-function texture stages. The mapping layer on the console does not
produce a usable pipeline for that combination, so such draws were skipped. Source issues a few
per frame, and in Portal the portal views depend on them: they rendered black.

The runtime now emulates the first texture stage with a generated `ps_2_0` shader
(`ffps::Build`, cached by `Dev::FfPs` under a key made from the stage-0 state and the bound
texture type).

| Covered | Detail |
|---|---|
| Colour and alpha operations | `DISABLE`, `SELECTARG1`, `SELECTARG2`, `MODULATE`, `MODULATE2X`, `MODULATE4X`, `ADD`, `SUBTRACT` |
| Arguments | `DIFFUSE`, `CURRENT`, `TEMP` (vertex colour 0), `SPECULAR` (vertex colour 1), `TEXTURE`, `TFACTOR`, `CONSTANT` |
| Argument modifiers | `COMPLEMENT`, `ALPHAREPLICATE` |
| Texture types | 2D, cube, volume, sampled with the stage's texture-coordinate index; white if no texture is bound |

| Not covered | Effect |
|---|---|
| Stages 1 to 7 | Ignored; the result is stage 0's output |
| Other operations (`ADDSIGNED`, `BLEND*`, `DOTPRODUCT3`, `LERP`, bump mapping, ...) | Treated as `MODULATE` |
| Fixed-function fog, specular add | Not applied |
| Texture-coordinate transforms and generation | Not applied |
| Vertex shader 3.0 without a pixel shader | Still skipped (shader model 3 forbids mixing) |
| No vertex shader and untransformed vertices | Still skipped: there is no fixed-function vertex pipeline |

The texture factor is passed in pixel constant register 31. The game's own value for that
register is saved and restored before the next draw that uses a real pixel shader (`ffC31`).

Log lines: `D9 ffps #N key=... ok` when a variant is built; `D9 ffsig #N EMULATED|SKIPPED ...`
for each distinct state signature (bounded); `D9 fixed-function draw emulated #N` and
`D9 fixed-function draw skipped #N ps= vs= preT= fvf=` as running counts. Each present line
carries `ffSkips=`. Set `gh_d9_ffps` to 0 to restore the old skip behaviour when bisecting.

## 7. D3DX and module identity

### `gh_d3dx9.h`

Source's 64-bit shader API DLL imports fourteen functions from `d3dx9_42.dll`, which the console
lacks. `gh_d3dx9.h` implements exactly those: twelve matrix and vector helpers (row-vector
convention, as D3DX), `D3DXCreateMatrixStack` (`ghdx::Stack`), and `D3DXCompileShader`, which is
forwarded to the `d3dcompiler_47.dll` the game ships. Anything else from D3DX is absent.

This file serves 64-bit guests. There are no D3DX beds on the 32-bit side: a 32-bit game that
ships its own D3DX DLL has it mapped as guest code, and one that expects a system copy would need
beds written.

### `GhD3d9Module`

`LoadLibrary("d3d9.dll")` and the `d3dx9_*` names return the pinned mapping-layer module as a
stand-in handle, and `GetProcAddress` on it is answered from the loader's shim table
(`Direct3DCreate9`, the `D3DPERF_*` no-ops, the D3DX names). This applies only while a guest is
running. Before that, a probe for `D3D9.DLL` must keep failing, because other code in the
process uses that probe to decide whether a desktop graphics stack exists.

## 8. Present

The D3D9 swap chain is ours and is never shown directly. Presentation goes through the same
bridge every other guest path uses ([graphics.md](graphics.md)).

`Dev::DoPresent`:

1. On first use, creates a D3D9 render target matching the bridge swap chain's size and format,
   asks the mapping layer for the `ID3D12Resource` behind it (a private entry in the versioned
   table), and publishes that resource to the bridge as the guest's frame. Logs
   `D9 present target ...`.
2. Each frame, blits back buffer 0 into that target with linear filtering, preserving aspect
   ratio (black bars are filled when the game's resolution has a different shape).
3. Returns the target to the common resource state, flushes the mapping layer's command stream,
   and calls the bridge's present. A presentation interval of "immediate" presents without
   waiting for vertical sync; anything else waits for one.

A periodic line `D9 present #N draws= ffSkips=` gives the frame count and draw statistics.

Consequences: the game's back-buffer size is independent of the output resolution; there is no
exclusive full-screen mode; `GetFrontBufferData` and additional swap chains are not implemented.

## 9. The 32-bit face (`x86/gh_x86_com_d3d9.h`)

A 32-bit game gets the same runtime. The x86 COM layer ([x86-guest.md](x86-guest.md), section 9)
wraps each 64-bit interface pointer in a guest object with a 32-bit vtable. Most of the roughly
119 device methods take only scalars and interface pointers and go through the generated tables
(`com_register_generated_d3d9`, produced by `toolchain/gen_com_tables.py` from the SDK's D3D9
headers). `com_apply_d3d9_overrides` hand-writes the rest:

| Area | Why it needs an override |
|---|---|
| `CreateDevice`, `Reset`, `GetPresentParameters` | `D3DPRESENT_PARAMETERS` is 56 bytes on x86 and 64 on x64 (the window handle moves); `read_pp32` / `write_pp32` translate |
| `GetCreationParameters` | 16 bytes versus 24 |
| `GetAdapterIdentifier` | 1100 bytes versus 1104. Writing the larger struct overwrote the guest's stack |
| `LockRect`, `LockBox`, vertex and index buffer `Lock` | The host pointer may be above 4 GB; see below |
| `Release` on lockable objects | Frees the lock bookkeeping |

**Lock bounce buffers.** If the pointer a lock returns is below 4 GB it is given to the guest as
is. Otherwise `d9_bounce_in` allocates a guest-heap buffer of the locked span, copies the current
contents in unless the lock is a discard, and returns that. `d9_bounce_out` copies back before
the host unlock. Two details matter for speed and correctness:

- The guest pointer is offset so that it has the same alignment modulo 64 as the host pointer.
  Source fills vertex buffers with non-temporal SSE stores, which fault on a misaligned address.
- A dynamic buffer keeps its bounce buffer between locks; it is locked many times a frame.

`RegisterD3D9Beds` registers `Direct3DCreate9` (in the Launcher build only; the desktop test
host has no D3D9), a failing `Direct3DCreate9Ex`, and the `D3DPERF_*` no-ops.
`com_live_d3d9` exposes a device for the DirectDraw layer's presentation path.

Test guest: `tests/x86/d9guest.c` creates the object and a device, checks struct sizes and a
lock round trip, and exits with a bitmask (511 when all checks pass).

## 10. 64-bit use

A 64-bit Direct3D 9 game calls the runtime directly: its import of `Direct3DCreate9` resolves to
the loader's bed, which returns the `D3D9` object, and the game's vtable calls land in the
classes above with no marshalling. Garry's Mod (64-bit Source,
`corpus/titles/garrysmod.ghtitle.json`) runs this way and is the reason `gh_d3dx9.h` exists.
The runtime is identical for both bitnesses; only section 9 is x86-specific.

## 11. Knobs and diagnostics

| Knob | Default | Effect |
|---|---|---|
| `gh_d9_ffps` | 1 | Fixed-function pixel stage 0 emulation |
| `gh_d9_vendor`, `gh_d9_device` | `0x1002`, `0x6798` | Reported adapter identity |
| `gh_d9_vram_mb` | 1536 | `GetAvailableTextureMem` answer |
| `gh_d9_shlog` | 0 | Log each new vertex/pixel shader pair before its first draw (`D9 newpair`) and write the bytecode under the diag directory. For finding which shader a driver failure belongs to |
| `gh_d9_psolog` | 0 | Hook the D3D12 device's pipeline-state creation and log each result (`D9PSO ok` / `FAIL`) with the description's key fields |
| `gh_d9probe.txt` (file) | absent | Run the self-test from the Launcher |

Other lines: `D9 DDI <entry> hr=` (a driver call failed), `D9 draw STALL` (a draw has not
returned for several seconds; the usual cause is the driver compiling a pipeline), and every
`Once` line beginning `D9 `.

## 12. Known gaps

| Gap | Behaviour today |
|---|---|
| Fixed-function vertex pipeline (transform, lighting, texgen) | Draws skipped |
| Fixed-function texture stages beyond 0, fog | Not emulated |
| State blocks | Objects are created; capture and apply do nothing |
| Multisampling | Reported unsupported; a multisample type passed to a create call is dropped |
| `IDirect3D9Ex` | Creation fails |
| Additional swap chains, `GetFrontBufferData` | Refused |
| `ProcessVertices`, patches, surface `GetDC`, shared handles | Refused or ignored |
| Managed-texture read-back | Returns zeros |
| Volume texture mip generation | No-op |
| Lost device | Never reported |
| D3DX beyond the fourteen functions | Absent |

Two header comments are out of date: `gh_d3d9.h` still describes itself as holding only the
probe, and `gh_d3d9rt.h` opens by saying fixed function is not implemented before describing the
stage-0 emulation. The code is as described on this page.

## 13. How to add a missing method or state

1. **Find it.** Run the title and grep the diag for `D9 `. Unimplemented methods log once by
   name through `Once`.
2. **Implement it in the class** in `gh_d3d9rt.h`. For a state: add the shadow field, store in
   the setter, answer the getter from the shadow, and forward with
   `DDI(this, pfn<Entry>, hDev, &arg)`. Check `d3dumddi.h` for the entry and its argument struct,
   and confirm the mapping layer fills that entry (legacy entries are null). If the state has a
   D3D9 default that differs from zero, set it in `Dev::Defaults`.
3. **Take the lock** (`Lk l;`) and keep reference counting consistent: anything stored in device
   state uses `Bind()` / the internal count, not `AddRef`.
4. **A new flat export** (a function in `d3d9.dll` or D3DX, not a method) needs a `Bed_`
   function, its forward declaration, and an entry in the loader's shim table in
   `guest_loader.cpp`; see [api-shims.md](api-shims.md).
5. **For 32-bit guests**, ask whether the generic marshaller can carry the method: scalars and
   interface pointers in, at most one trailing interface out. If a struct with pointers or
   handles crosses, or a raw memory pointer is returned, add
   `c.override_method(id, "Name", argbytes, fn)` in `com_apply_d3d9_overrides`, with the exact
   stdcall argument byte count (including `this`). If the interface itself is missing, add it to
   `toolchain/gen_com_tables.py` and regenerate `gh_x86_com_gen.h`.
6. **Test.** Extend `tests/x86/d9guest.c` for the 32-bit path, or use the probe for the driver
   path, before running a game.

For a new fixed-function case, extend `ffps::Build` and the key it is cached under; keep the
`D9 ffsig` line accurate so a diag shows which signatures are emulated.
